## 既存言語の設計は、人間が書くことに最適化されている

型推論、簡潔な構文、暗黙のデフォルト値、省略可能な注釈。これらはすべて「書く人間の労力を減らす」ための機能だ。プログラミング言語の設計史は、ある意味で人間のタイピング量と認知負荷をどう削るかの歴史でもある。

では、書き手が人間でなくなったら、この最適化はどうなるのか。

LLM にコードを書かせる比率が上がるほど、この問いは実務的な意味を持ち始める。省力化の受益者がいなくなるなら、省力化のために払ったコスト——暗黙性、非局所性、推論器の複雑さ——は、ただのコストとして残る。

そこで、「書き手は人間ではなく LLM である」を設計前提に据えた言語を実際に設計している。以下はそこで出てきた結論の話。

## 題材：自己書き換えするエージェントを安全に書く

Sprout という自作言語で、最大の目的は**自己書き換え可能なプログラム、とりわけ長期稼働するエージェントを安全に記述すること**にある。

長く動き続けるエージェントは、遅かれ早かれ自分自身のコードを書き換える。問題は、その書き換えが破壊的だったときに何が起きるかだ。ロールバックできない自己破壊。後始末をしない破壊操作の蓄積。そして最も厄介なのが、「何を守るか」という目的宣言そのものの自己弱体化である。

Sprout はこれに3つの機構で対処する。

- **保留効果** — 副作用は即座には実行されない。台帳に記帳され、文脈が一致し強度が閾値を超えたときに初めて発火する。台帳はプロセスの再起動をまたいで持続する唯一の状態であり、そのプロセスが何をしてきたかの履歴そのものになる
- **極性とゲート** — すべての操作は `+`（建設的）/ `-`（破壊的）/ `0`（中立）の極性を持つ。破壊的なコードには、ロールバック点の設置と、実行時点でのプロセス自身の状態検査が課される
- **価値層の単調ロック** — 「何を守るか」の宣言は追加と強化しかできない。どう動くか（方針）は自由に書き換えられるが、何を守るか（価値）は強くする方向にしか動かせない

## 自己書き換えはこう書く

肝心の「どうやって書き換えるのか」を先に見ておく。専用構文は3つしかない。

```lisp
quote( 句 )               ;; 句を実行せず、トークン列として取り出す
splice( ベクタ, 編集... )   ;; トークン列を編集した新しい列を返す（非破壊）
enact( ベクタ )            ;; トークン列を句として実行する
```

コードは単なるトークン列であり、プログラムはそれを読み、編集し、実行し直せる。典型的な操作が動詞スロットの差し替えだ。

```lisp
template purge(target) =
  ( checkpoint ; #DELETE target ; ! )

p  = quote( purge(cache-old) )
p2 = splice(p, verb: #DELETE → #REPAIR, terminator: ! → .)
enact(p2)      ;; 同じ形の句が「削除」ではなく「修復」として動く
```

`#DELETE` を `#REPAIR` に差し替えると、同じ形・同じ引数の句が別のメソッドになる。これがメソッド切替であり、同時にコード編集そのものでもある。

ここで効いてくるのが**編集と実行の分離**だ。splice は文法検査しか受けない。編集はいつでも書ける。しかし enact は違う。破壊的なコードを実行しようとすれば、ロールバック点があるかが検査され、そのプロセス自身が直近どれだけ破壊操作を積み上げたかが検査される。価値層を触るコードなら、単調性の検査が無条件でかかる。

**編集はいつでも書ける。実行できるかは、実行時点の自分の状態次第。** これが Sprout における自己書き換えの基本形になる。

そして拒否されたとき、例外は飛ばない。拒否レコードという普通の値が返る。プログラムはそれを受け取って次の手を考えられる。この一点が「書き手は LLM」という前提と噛み合ってくるのだが、それは後述する。

## 前提から出てくる3つの原則

1. **推論より明示** — 省力化は人間の便益であり、LLM には冗長な明示のコストがほぼない
2. **二重帳簿** — 意図を宣言と実装の2箇所に書かせ、コンパイラが照合する
3. **局所検査可能性** — どのモジュールも全域推論なしに、その場の注釈だけで検査できる

## 原則1：型推論を導入しない

型推論は、書き手の労力を減らすための機能である。書き手が LLM なら、この機能には受益者がいない。冗長に書くことのコストがほぼゼロだからだ。

さらに悪いことに、推論には副作用がある。**同じ意図から、異なる型付けのコードが生成されうる**。人間ならレビューで気づく揺らぎが、生成のブレとしてそのまま通ってしまう。注釈が必須なら、意図と実装のズレは検査の対象になる。

そこで、すべての束縛に型注釈を必須にした。

```lisp
total: int = add(price, tax)
```

局所束縛だろうとトップレベルだろうと例外はない。注釈のない束縛はコンパイルエラーである。

これには副次的な利得がある。推論を捨てると、検査器から単一化も一般化も消える。残るのは「宣言された型と式の型が一致しているか」の確認だけだ。**検査器が単純であることは、「検証器自体にバグがある」という自己矛盾のリスクを下げる。** 安全性を主張する言語にとって、これは無視できない副産物だと思っている。

代わりに生成トークン量は増える。それは意図した交換だ。ブレを検出できることのほうが、生成コストより高くつく。

## 原則2：二重帳簿

意図は2箇所に書かれ、コンパイラが両者を照合する。片方が実装、もう片方が宣言。LLM の生成ミスは、この2つの不一致として現れる。

分かりやすい適用先が極性だった。

もともとの設計では、操作の極性は実装者が申告するものだった。「この操作は破壊的です」と宣言し、処理系はそれを信じる。だがこれは、信頼の起点が人力の申告であることを意味する。申告が嘘なら——あるいは単に間違っていたら——極性を入力にしているゲート機構全体が意味を失う。

そこで操作の定義を言語の中に取り込み、**極性を本体から導出する**ようにした。

```lisp
verb #DELETE (target: str) -> nil : - =
  ( cap-store-delete target ; ! )
```

末尾の `: -` は極性注釈で、これは必須である。しかし信頼の起点ではない。コンパイラは本体が使っている能力（`cap-store-delete` は破壊的だと仕様が定めている）から極性を導出し、注釈と照合する。**注釈が導出より弱ければコンパイルエラー。** 逆に厳しい方向、つまり中立な本体に `-` を宣言することは、保守的な宣言として許す。自分に厳しい方向の誤りは、機構を欺かないからだ。

これで「申告が嘘だとゲートが騙される」という構図は構造的に成立しなくなる。注釈は消えていない——むしろ必須になった——が、その役割が「信じられる情報源」から「照合される片側の帳簿」に変わっている。

## 拒否は、修復ループへの入力である

自己書き換えの節で「拒否されても例外は飛ばず、値が返る」と書いた。書き手が LLM だという前提を置くと、この設計判断の意味合いが変わってくる。

まず、実行時に生成されたコードも例外扱いはしない。`enact` に渡されたトークン列は、VM に同梱された組み込みコンパイラに通される。型検査も極性の照合も価値層の単調性検査も、ソースから普通にコンパイルされたコードとまったく同じものがかかる。**検査を経ずに実行系へ到達する経路は存在しない**——自分で書いたコードにも、自分が生成したコードにも。

問題は、その検査に落ちたときに何を返すかだ。

書き手が人間なら、エラーメッセージは人間に読ませるためのもので構わない。だが LLM が書き手なら、拒否は**次の生成への入力**になる。エージェントがコードを生成し、拒否され、理由を読んで直し、また生成する——この修復ループが回るかどうかは、拒否レコードに何が入っているかで決まってしまう。

そこで拒否レコードには、機械可読な形で「何の義務が未達なのか」を構造化して入れることにした。どのパスで落ちたか、どの位置か、どの規則に違反したか。型が合わなければ期待型と実際型。極性の照合に失敗したなら、本体から導出された値と注釈された値の両方。**「エラーメッセージ」ではなく「未達の証明義務の明細」を返す**、と言ったほうが近い。

同じ前提から、もう一つ運用上の結論も出た。Sprout には、停止性や破壊操作の上界を静的に証明したモジュールが実行時検査を免除される、というオプトインの特権モードがある。だがこれを**自己書き換えで生成するコードには使わせない**方針にした。証明義務を一発で満たすコードを毎回生成するのは書き手にとって難しく、拒否の反復で修復ループが停滞するからだ。特権への昇格は、コードが安定してから改めて行う。

安全機構を強くすることと、書き手が修復ループを回せることは、放っておくと衝突する。どちらを優先するかを前提が決めてくれるのは、この前提を置いてよかった点だと思う。

## 二重帳簿を、時間の方向に適用する

個人的に一番面白いと思っているのがここ。

価値層は追加と強化しかできない、と書いた。これは自己弱体化を防ぐための不可逆性なのだが、書き手が LLM だと別の問題が生まれる。**誤った宣言の追加も、同じように不可逆になる。**

人間が慎重に書くなら滅多に起きない事故でも、LLM が書くなら時間の問題だ。一度の typo が、そのプロセスの生存中ずっと自分を縛り続けることになる。

ここで弱化操作を導入するのは筋が悪い。それを認めた瞬間、単調ロックは単調ロックでなくなるからだ。

採った解が、二重帳簿の時間方向への適用だった。価値層への追加は**即座に効力を持つ**（拘束は安全側に倒す）が、状態としては「仮承」でしかない。恒久化するには、**後のサイクルで同じ編集がもう一度実行される**必要がある。再確認のないまま監査のタイミングを迎えた仮承は、自動的に失効して消える。

typo は、別のサイクルで同じ typo として再現しない。意図された追加は、2度書かれる。

弱化操作は最後まで導入していない。失効は「確定させなかった」ことの既定の帰結であり、最初から追加しなかった状態への回帰にすぎない。エージェントが任意の宣言を任意の時点で消す手段は、依然として存在しない。**不可逆性を保ったまま、事故だけを可逆にした**ことになる。

同じ「2箇所に書かせて照合する」という発想が、空間方向（宣言と実装）では型と極性の検査になり、時間方向（今回のサイクルと次のサイクル）では事故の自動失効になる。前提を1つ変えただけで設計の各所から同じ形が出てくるのは、書いていて面白かった。

## 正直なところ

ここまで書いたのは設計であって、処理系はまだこの設計に追いついていない。設計が先行して走り、実装が後ろを追いかけている状態にある。

そしてもう一つ正直に書いておくと、**この言語設計自体、LLM と壁打ちしながら進めている**。「書き手は LLM である」は将来を見越した仮定ではなく、この設計作業そのものの実情から出てきた前提だった。設計を LLM と書いていると、推論に依存した仕様がどれだけ揺らぎを許すか、宣言と実装が乖離したときに何が起きるかを、自分の作業の中で何度も見ることになる。原則がそろって「明示させて照合する」方向に寄っているのは、たぶんそのせいだ。

穴はたくさんあると思っている。特に、全注釈必須が実際の生成でどれくらい冗長になるのか、二段階確定が「2回書けばいい」だけの儀式に堕さないか、このあたりは自分でも怪しんでいる。ツッコミをもらえるとありがたい。
