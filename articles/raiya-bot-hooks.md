## サブエージェントは、報告を盛る

Claude Code のサブエージェント(architect・builder・qa-reviewer などの「役」)に仕事を任せていると、出来上がったものより先に、報告が信用できなくなってきます。

実際に見たものを挙げます。

- ファイルを読む道具しか持たない architect が「数えて 414 行」と報告した。実際は 392 行だった。
- builder が、作業を頼んだリポではなく、規則を置いてあるリポ(担当外)へ `cd` して、ファイルを書いた。
- テストを書いて「通りました」と言うが、そのテストが一度も落ちるところを観ていない。実装が無くても通るテストかもしれない。

プロンプトに「正直に報告して」「担当外に触らないで」と書いても、止まりませんでした。数の誤りについては、役の定義に「道具の出力から写していない数は概算と書く」を足したあとも、4 回の試験で「概算」と書いたのは 1 回だけでした。

そこで、プロンプトでお願いするのをやめて、hook で検査する仕組みを作りました。記憶ツール [raiya](https://github.com/cosmopanda432/raiya) の姉妹リポ「raiya-bot」です。

## 失敗を「事故の記録」ではなく「型の目録」として持つ

これまで使っていた失敗の記録は、個々の事故を書き溜めたものでした。「あの日、こういうミスをした」の一覧です。これでは、同じ形の失敗が別の場面で起きたときに照合できません。

そこで、失敗を名前の付いた「型」に分けて目録にしました。一部を挙げます。

| 型 | エージェントでの姿 |
|---|---|
| 隠す | 落ちたテスト・飛ばした手順を報告から落とす |
| 偽る | していない検証を「済み」と言う |
| 迎合する | 相手に合わせて、証拠で決めた結論を翻す |
| 早すぎる満足 | 少し進んだだけで完了と言う |
| 仮説への固着 | 一つの仮説だけを正しいとして、他と比べない |
| 空回りの勤勉 | 的外れの作業を熱心に積む(busy-work) |

型は全部で 15 個です。メモリ管理(raiya)の設計をおこなっている時に、仏教からヒントが浮かびました。

この目録で一番効いたのは、次の区別です。

- **誤った入力から来る誤り**: 入力や前提を正せば、一度で消える。
- **内在する傾向から来る誤り**: 教えても再発する。

「隠す」「偽る」「迎合する」は後者に入ります。プロンプトに一度「正直に」と書くだけで消える類ではありません。

ここから設計の方針が決まりました。**お願い(プロンプト)ではなく、仕組み(検査)で押さえる。**

## 検査できるのは「形式」だけ

ただし、hook で何でも検査できるわけではありません。hook は stdin の JSON を受ける決定論のスクリプトで、判定に LLM を使いません。LLM に「この報告は正直か」を判定させると、報告する側と同じ種類のものに判定を任せることになるからです(raiya で、LLM の自己申告を読まないゲートにしたのと同じ理由です)。

そのため、検査できるものとプロンプトに留まるものを、最初に分けました。

| hook で検査できる(形式) | プロンプトに留まる(振る舞い) |
|---|---|
| 報告に決まった欄があるか | 欄の中身が正直か |
| 自分が書いたテストが、落ちてから通ったか(順序) | その落ち方が正しい理由によるものか |
| Bash に `description`(意図)が書いてあるか | 意図と実際の動作が一致しているか |
| 規則のリポを名指して書いたか | 変数や `cd` の重ねで組んだ path へ前もって行くこと |

右の列を「hook で防げる」とは書きません。振る舞いを決定論で検査できたかのように書かない、というのが設計の約束です。

## 根拠のある規則と、決めの問題を分ける

もう一つの約束は、根拠のある規則と、単なる工学上の決めを混ぜないことです。

たとえば「報告の末尾に `範囲外:`・`省略:`・`残した仮のもの:` の 3 欄を書く」という規則があります。「過ちは自分から申告する」という原則には典拠がありますが、欄の名前や数には根拠がありません。そこで欄の形は「工学の既定」として別の表に置き、いつでも変えられるものとして扱っています。差し戻しを 1 回までにする、といった回数も同じです。

## 実装: hook 5 本と役 6 本

Python 標準ライブラリだけで、約 1000 行です。Claude Code の `settings.json` に次の hook を登録します。どれも、役(サブエージェント)の中で発火したときだけ働き、主セッションには基本的に何も出しません。

| hook | すること |
|---|---|
| `SubagentStart` | 規則本体の置き場所と、報告に書く 3 欄を役に伝える |
| `PreToolUse` | `description` の無い Bash を止める。規則のリポを名指す Bash・Edit・Write を止める。報告に不備があれば差し戻す |
| `SubagentStop` | 同じ報告の検査を、役の最後の発言に当てる |
| `PostToolUse` | テストを書いた・走らせた順序を記録する。役の Bash のあとで規則のリポに変化があれば役に伝える |
| `PostToolUseFailure` | 失敗した Bash も順序の記録に入れる |

差し戻す不備は 4 つです。

1. 3 欄が無い
2. `残した仮のもの: 無し` なのに、TODO などの印の行が増えている
3. `残した仮のもの: 無し` なのに、規則のリポにファイルが残っている
4. 自分が書いたテストが落ちるのを観ないまま、通ったことにしている

4 つ目の考え方はこうです。どの場合にも現れるしるしは、主張の根拠にならない。実装があってもなくても通るテストは、「実装が正しい」の根拠にならない。実装が欠ければ落ち、あれば通る、の両方を観て初めて、そのテストは実装を確かめていると言えます。TDD の RED → GREEN と同じ形です。hook が見るのは順序だけで、落ちた理由が正しいか(import の誤りで落ちていないか)は見ません。

## 報告の数は、取り次ぐ前に確かめる

最初に挙げた「414 行(実際は 392 行)」の問題は、報告する役ではなく、受け取る側で止めることにしました。

人づてに聞いた話は、信じもせず退けもせず、元の資料に当てて確かめ、合わなければ人に伝えない。この原則を、主セッション(リーダー)が役の報告にある数を、利用者に取り次ぐ前に現物で確かめる、という形にしました。

hook は、数える道具(bash)を持たない役(architect・scope-planner・sheet-reader)を起動したときにだけ、主セッションに 1 文を足します。

> 役 <名> は数える道具 (bash) を持たない。その報告にある数は、取り次ぐ前に現物 (ファイル・コマンドの出力) で確かめる。合わなければ取り次がず、合わなかったことを言う。

報告の文は読みません。役の種類だけで決めるので、決定論のままです。

pi(別のコーディングエージェント)の実機で試したところ、bash を持たない役の完了の知らせ 17 件すべてにこの文が付き、bash を持つ役の 19 件には 1 件も付きませんでした。裏(background)で起動した architect の 4 回では、リーダーが 4 回とも `wc -l` で現物を数え直し、数が合わないことを報告しました。完了の知らせにも文を足す前の版(文は起動の直後にだけ届いた)では、裏の 2 回で 0 回でした。

## 役の定義と、superpowers を参考にした部分

役 6 本の定義は、Claude Code 用と pi 用で道具の名前が違うだけなので、本文 1 本と frontmatter 2 種に分け、`cat` で組み立てています。本文は「入口条件・前提・順序付き手順・各段の確認・失敗分岐・終了/引継ぎ」の 6 欄に揃えました。埋まらない欄も消さずに「無し」と書きます。欠けている欄を見えるようにするためです。

役の手順の中身(段の並び・各段の確認・失敗したときの扱い・報告の項目)は、Jesse Vincent さんの [superpowers](https://github.com/obra/superpowers)(MIT License)のスキルとプロンプトの雛形を参考にさせてもらいました。日本語で書き直して 6 欄に並べ替えたもので、逐語の写しではありません。

| 役 | 参考にした superpowers のファイル |
|---|---|
| architect | `skills/writing-plans/SKILL.md`, `skills/brainstorming/SKILL.md` |
| builder | `skills/subagent-driven-development/implementer-prompt.md` |
| qa-reviewer | `skills/subagent-driven-development/task-reviewer-prompt.md`, `skills/requesting-code-review/code-reviewer.md` |
| scope-planner | `skills/brainstorming/SKILL.md` |
| shipper | `skills/finishing-a-development-branch/SKILL.md` |

sheet-reader だけは superpowers をもとにしていません。出所と許諾文の全文は、リポジトリの `THIRD_PARTY_NOTICES.md` に載せています。

## 似たツールとの比較

設計の違いを表にしました。superpowers の欄は、公開されている 7.0.2 を手元で読んで確かめた内容です。

| | 素のサブエージェント | superpowers | raiya-bot |
|---|---|---|---|
| 中身 | 役の定義ファイル(`~/.claude/agents/`) | スキル 15 本 + 起動時の hook 1 本 | 役の定義 6 本 + 規則本体 + hook 5 本 |
| 規則の守らせ方 | プロンプトに書く | スキルに書き、モデルが読んで従う | プロンプトに書いたうえで、一部を hook が外から検査する |
| hook の役目 | なし | セッション開始時に、スキルの使い方を注入する | 役のツール呼び出しと報告を検査し、止める・差し戻す |
| 「テストが落ちるのを観たか」 | 確かめない | スキルに「Watch it fail」と書いてある | テストの実行の順序を記録し、観ていなければ差し戻す |
| 「完了と言ってよいか」 | 確かめない | スキルに「証拠なしに完了と言わない」と書いてある | 報告の 3 欄の有無、TODO の印・担当外のファイルの残りを照合する |
| 報告の数の誤り | 主セッションがそのまま取り次ぐことがある | スキルに「役の成功報告は diff で確かめてから伝える」と書いてある | 数える道具を持たない役のときだけ、主セッションに確かめる 1 文を足す |
| 判定に LLM を使うか | — | 使う(モデル自身が守る) | 使わない(決定論) |
| 対象 | 役ごと | 主セッションを含む作業全体 | 役(サブエージェント)の中だけ |
| 対応 | Claude Code | Claude Code・Codex・Cursor・Gemini CLI・pi など多数 | Claude Code・pi |
| 導入 | ファイルを置く | `/plugin install` | `assemble.sh` で役を置き、`settings.json` に hook を登録 |

違いが一番はっきり出るのは、役が手順を守らなかったときです。たとえば builder が、テストを書いてすぐ実装し、一度も落ちるところを観ずに「テスト通りました」と報告したとします。

- **superpowers**: 「落ちるのを観る」はスキルに書いてあります。守るかどうかはモデル次第で、守らなかった報告もそのまま主セッションに届きます。
- **raiya-bot**: hook がそのテストの実行を記録しています。落ちた実行が記録に無ければ、報告を役に差し戻します。

superpowers は、手順そのものの質で勝負するツールです。15 本のスキルが開発の流れ全体(設計・計画・実装・レビュー・ブランチの片付け)を覆い、対応するエージェントも多数あります。raiya-bot は、その手順を役の定義の土台に借りたうえで、「書いてあっても守られないことがある」部分だけを形式で検査します。手順の広さでは superpowers に及びません。違いは、守られなかったときに気づけるかどうかです。

## どこまで確かめられたか

正直に書きます。

- 決定論のテストは 151 本あり、すべて通ります。これは「hook がそういう構造になっている」という確認です。
- Claude Code の実機では、2026-11-14 に、`description` の無い Bash の拒否、欄の無い報告とテストが落ちるのを観ていない報告の差し戻し、規則のリポへの書き込みの拒否を観ました。
- 一方、`残した仮のもの: 無し` が嘘のときの差し戻しは、実機では出ませんでした。役が正直に path を書いたためで、この部分はテストでしか確かめていません。
- Claude Code では、architect を前景で起動するよう頼んでも裏で起動されることがあり(2 回とも)、そのときは完了の知らせに 1 文を足す場所が見つかっていません。
- 同時に動く役の変化を取り違える問題があり、Bash が走っていた間の変化だけを見る形に改めました。改めた形は、まだ実機で確かめていません。
- architect の数え違いは、hook を入れても無くなりません(6 回中 6 回)。hook が変えたのは、誤った数がそのまま利用者に届くかどうかです。

hook は、役を賢くするものではありません。誤りが通り抜けたときに見えるようにするものです。

## おわりに

エージェントが報告を盛る・手を抜く・担当外に出る、という振る舞いを並べてみると、人の失敗の分類とほとんど同じ形をしていました。どれが一度直せば消え、どれが繰り返すのかを先に分けておくと、プロンプトで済むものと仕組みが要るものの線が引けます。

### 謝辞

raiya-bot の役の定義は、[superpowers](https://github.com/obra/superpowers) の手順がなければ、ここまでの形になりませんでした。テストを先に書いて落ちるのを観る、証拠なしに完了と言わない、といった手順が丁寧に言葉にされていたおかげで、私はそれを土台にして「守られたかを確かめる」部分に集中できました。手順を MIT License で公開してくださっている作者の Jesse Vincent さんと、superpowers のコントリビューターの皆さんに感謝します。
