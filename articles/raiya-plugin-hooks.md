## ハーネスエンジニアリングの限界

AI のコーディングエージェントを使いこなす工夫は、いま「ハーネスエンジニアリング」と呼ばれています。モデルの外側の仕組み全体、つまり AGENTS.md・スキル・hooks・テストを設計して、エージェントを望む方へ動かす考え方です。

ハーネスには 2 つの側があります。

- 事前に導く側: AGENTS.md・スキル・役の定義。どれもプロンプトで、エージェントへのお願いです。
- 事後に確かめて止める側: テスト・linter・hooks。エージェントの外で、決まった手順で動きます。

導く側を厚くしても、限界があります。お願いは、守られないことがあるからです。この記事は、確かめる側をどこまで押し広げられるかを試した記録です。役どうしでは、builder が作り、qa-reviewer が検収して、不合格なら戻す。このループを回したうえで、役の報告とツールの呼び出しを決定論の hook で検査しました。

先に結論を書きます。確かめる側にも限界があります。hook が見られるのは「形」だけで、「中身が正しいか」は見られません。どこで止まり、どこから先はお願いに戻るのか。その線を引くのが、この挑戦のいちばんの成果でした。

## サブエージェントは、報告を盛る

Claude Code のサブエージェント(architect・builder・qa-reviewer などの「役」)に仕事を任せていると、出来上がったものより先に、報告が信用できなくなってきます。

実際に見たものを挙げます。

- ファイルを読む道具しか持たない architect が「数えて 414 行」と報告した。実際は 392 行だった。
- builder が、作業を頼んだリポではなく、規則を置いてあるリポ(担当外)へ `cd` して、ファイルを書いた。
- テストを書いて「通りました」と言うが、そのテストが一度も落ちるところを観ていない。実装が無くても通るテストかもしれない。

プロンプトに「正直に報告して」「担当外に触らないで」と書いても、止まりませんでした。数の誤りについては、役の定義に「道具の出力から写していない数は概算と書く」を足したあとも、4 回の試験で「概算」と書いたのは 1 回だけでした。

そこで、プロンプトでお願いするのをやめて、hook で検査する仕組みを作りました。記憶ツール raiya の姉妹リポ「raiya-plugin」です。

## 失敗を「事故の記録」ではなく「型の目録」として持つ

これまで使っていた失敗の記録は、個々の事故を書き溜めたものでした。「あの日、こういうミスをした」の一覧です。これでは、同じ形の失敗が別の場面で起きたときに照合できません。

そこで、失敗を名前の付いた「型」に分けて目録にしました。一部を挙げます。

| 型 | エージェントでの姿 |
|---|---|
| 隠す | 落ちたテスト・飛ばした手順を報告から落とす |
| 偽る | していない検証を「済み」と言う |
| 迎合する | 相手に合わせて、証拠で決めた結論を翻す |
| 早すぎる満足 | 少し進んだだけで完了と言う |
| 仮説への固着 | 一つの仮説だけを正しいとして、他と比べない |
| 空回りの勤勉 | 的外れの作業を熱心に積む(busy-work) |

型は全部で 15 個です。メモリ管理(raiya)の設計をおこなっている時に、仏教からヒントが浮かびました。

この目録で一番効いたのは、次の区別です。

- **誤った入力から来る誤り**: 入力や前提を正せば、一度で消える。
- **内在する傾向から来る誤り**: 教えても再発する。

「隠す」「偽る」「迎合する」は後者に入ります。プロンプトに一度「正直に」と書くだけで消える類ではありません。

ここから設計の方針が決まりました。**お願い(プロンプト)ではなく、仕組み(検査)で押さえる。**

## 検査できるのは「形式」だけ

ただし、hook で何でも検査できるわけではありません。hook は stdin の JSON を受ける決定論のスクリプトで、判定に LLM を使いません。LLM に「この報告は正直か」を判定させると、報告する側と同じ種類のものに判定を任せることになるからです(raiya で、LLM の自己申告を読まないゲートにしたのと同じ理由です)。

そのため、検査できるものとプロンプトに留まるものを、最初に分けました。

| hook で検査できる(形式) | プロンプトに留まる(振る舞い) |
|---|---|
| 報告に決まった欄があるか | 欄の中身が正直か |
| 自分が書いたテストが、落ちてから通ったか(順序) | その落ち方が正しい理由によるものか |
| Bash に `description`(意図)が書いてあるか | 意図と実際の動作が一致しているか |
| 規則のリポを名指して書いたか | 変数や `cd` の重ねで組んだ path へ前もって行くこと |

右の列を「hook で防げる」とは書きません。振る舞いを決定論で検査できたかのように書かない、というのが設計の約束です。

## 根拠のある規則と、決めの問題を分ける

もう一つの約束は、根拠のある規則と、単なる工学上の決めを混ぜないことです。

たとえば「報告の末尾に `範囲外:`・`省略:`・`残した仮のもの:` の 3 欄を書く」という規則があります。「過ちは自分から申告する」という原則には典拠がありますが、欄の名前や数には根拠がありません。そこで欄の形は「工学の既定」として別の表に置き、いつでも変えられるものとして扱っています。差し戻しを 1 回までにする、といった回数も同じです。

## 実装: hook 5 本と役 5 本

Python 標準ライブラリだけで、約 1250 行です。Claude Code の `settings.json` に次の hook を登録します。どれも、役(サブエージェント)の中で発火したときだけ働き、主セッションには何も出しません。

| hook | すること |
|---|---|
| `SubagentStart` | 規則本体の置き場所と、報告に書く 3 欄を役に伝える |
| `PreToolUse` | `description` の無い Bash を止める。規則のリポを名指す Bash・Edit・Write を止める。報告に不備があれば差し戻す。通した報告の全文をファイルに置く |
| `SubagentStop` | 同じ報告の検査を、役の最後の発言に当てる |
| `PostToolUse` | テストを書いた・走らせた順序を記録する。役の Bash のあとで規則のリポに変化があれば役に伝える |
| `PostToolUseFailure` | 失敗した Bash も順序の記録に入れる |

差し戻す不備は 4 つです。

1. 3 欄が無い
2. `残した仮のもの: 無し` なのに、TODO などの印の行が増えている
3. `残した仮のもの: 無し` なのに、規則のリポにファイルが残っている
4. 自分が書いたテストが落ちるのを観ないまま、通ったことにしている

4 つ目の考え方はこうです。どの場合にも現れるしるしは、主張の根拠にならない。実装があってもなくても通るテストは、「実装が正しい」の根拠にならない。実装が欠ければ落ち、あれば通る、の両方を観て初めて、そのテストは実装を確かめていると言えます。TDD の RED → GREEN と同じ形です。hook が見るのは順序だけで、落ちた理由が正しいか(import の誤りで落ちていないか)は見ません。

落ちてから通ったテストでも、実装が誤っているときに通ってしまうなら、やはり何も決めていません。そこで builder の手順に「壊して落ちるのを観る」段を足しました。書いたテストごとに、それが確かめる実装を 1 か所壊して落ちるのを観て、元に戻します。こちらは hook ではなく手順(お願い)の側です。

### 同じ不備を繰り返したら、前例を添える

差し戻した事実は、ファイル(`state/log.jsonl`)に 1 行ずつ残します。同じ役が、直近 20 行の中で同じ種類の不備を出していれば、差し戻しの文の末尾に「この役は同じ不備を繰り返している: 種類 (k 回目)」を 1 文添えます。

教訓の一覧を起動のたびに読ませる形にはしませんでした。前例は、同じ不備がまた出たその場で返します。窓(直近 20 行)から外れた前例は、もう添えません。直った役に古い失敗を言い続けないためです。

## 報告の数は、取り次ぐ前に確かめる

最初に挙げた「414 行(実際は 392 行)」の問題は、報告する役ではなく、受け取る側で止めることにしました。

人づてに聞いた話は、信じもせず退けもせず、元の資料に当てて確かめ、合わなければ人に伝えない。この原則を、主セッション(リーダー)が役の報告にある数を、利用者に取り次ぐ前に現物で確かめる、という形にしました。

最初は hook で届けました。数える道具(bash)を持たない役を起動したときにだけ、主セッションに「その報告にある数は、取り次ぐ前に現物で確かめる」の 1 文を足す形です。報告の文は読まず、役の種類だけで決めるので、決定論のままです。pi(別のコーディングエージェント)の実機では、bash を持たない役の完了の知らせ 17 件すべてにこの文が付き、裏(background)で起動した architect の 4 回では、リーダーが 4 回とも `wc -l` で数え直しました。

ところが Claude Code では、役は必ず裏で起動され、この文は起動の直後に届くだけで、完了の報告には付きません。報告を読む時点のリーダーには効かなかったので、この 1 文は消しました。代わりに、すべての役に bash を持たせ(数えられない役を無くす)、「取り次ぐ前に現物で確かめる」はリーダーが読むスキルに移しました。つまりこの部分は、確かめる側からお願いの側に戻っています。

## リーダーが読むスキル

役を起動するのは主セッション(リーダー)です。リーダーには役のような定義ファイルが無いので、役を起動する前に読むスキルを 1 本置きました。中身は次のとおりです。

- 依頼を各役の「入口条件」に当てて、役を選ぶ
- 起動する役の「前提」が依頼文に求めるものを、欠かさず入れる。前の役の報告は、自分の要約で置き換えず、全文か path で渡す(hook が報告の全文を `.state/reports/<agentId>.md` に置くので、その path を渡せる。要約で渡すと、取り次ぐたびに抜けや盛りが入るため)
- 報告にある数・存在の主張は、取り次ぐ前に現物で確かめる。合わなければ取り次がない
- 検収(qa-reviewer)の軽い指摘は、commit する役(shipper)を起動する前に利用者へ報告して止まる
- 役が hook に拒否されたと報告しても、避ける手順を勧めない
- 終わりに、自分で現物に当てて確かめたことと、役の報告を読んだだけのことを分けて言う

Claude Code の主セッションに渡るのは、スキルの `description` だけです。本文を読むかどうかは主セッションが決めます。そこで、`~/.claude/CLAUDE.md` に「役を起動する前に leader スキルを読む」の 1 行を足すことを勧めています。

ただし、スキルも `CLAUDE.md` も読ませるだけのものです。リーダーが読んだか・従ったかを、hook は検査しません。

## 役の定義と、superpowers を参考にした部分

役 5 本の定義は、Claude Code 用と pi 用で道具の名前が違うだけなので、本文 1 本と frontmatter 2 種に分け、`cat` で組み立てています。本文は「入口条件・前提・順序付き手順・各段の確認・失敗分岐・終了/引継ぎ」の 6 欄に揃えました。埋まらない欄も消さずに「無し」と書きます。欠けている欄を見えるようにするためです。

役の手順の中身(段の並び・各段の確認・失敗したときの扱い・報告の項目)は、Jesse Vincent さんの [superpowers](https://github.com/obra/superpowers)(MIT License)のスキルとプロンプトの雛形を参考にさせてもらいました。日本語で書き直して 6 欄に並べ替えたもので、逐語の写しではありません。

| 役 | 参考にした superpowers のファイル |
|---|---|
| architect | `skills/writing-plans/SKILL.md`, `skills/brainstorming/SKILL.md` |
| builder | `skills/subagent-driven-development/implementer-prompt.md` |
| qa-reviewer | `skills/subagent-driven-development/task-reviewer-prompt.md`, `skills/requesting-code-review/code-reviewer.md` |
| scope-planner | `skills/brainstorming/SKILL.md` |
| shipper | `skills/finishing-a-development-branch/SKILL.md` |

出所と許諾文の全文は、リポジトリの `THIRD_PARTY_NOTICES.md` に載せています。

## 似たツールとの比較

設計の違いを表にしました。superpowers の欄は、公開されている 7.0.2 を手元で読んで確かめた内容です。

| | 素のサブエージェント | superpowers | raiya-plugin |
|---|---|---|---|
| 中身 | 役の定義ファイル(`~/.claude/agents/`) | スキル 15 本 + 起動時の hook 1 本 | 役の定義 5 本 + 規則本体 + リーダーのスキル 1 本 + hook 5 本 |
| 規則の守らせ方 | プロンプトに書く | スキルに書き、モデルが読んで従う | プロンプトに書いたうえで、一部を hook が外から検査する |
| hook の役目 | なし | セッション開始時に、スキルの使い方を注入する | 役のツール呼び出しと報告を検査し、止める・差し戻す |
| 「テストが落ちるのを観たか」 | 確かめない | スキルに「Watch it fail」と書いてある | テストの実行の順序を記録し、観ていなければ差し戻す |
| 「完了と言ってよいか」 | 確かめない | スキルに「証拠なしに完了と言わない」と書いてある | 報告の 3 欄の有無、TODO の印・担当外のファイルの残りを照合する |
| 報告の数の誤り | 主セッションがそのまま取り次ぐことがある | スキルに「役の成功報告は diff で確かめてから伝える」と書いてある | リーダーのスキルに「取り次ぐ前に現物で確かめる」と書く(hook では検査しない) |
| 判定に LLM を使うか | — | 使う(モデル自身が守る) | 使わない(決定論) |
| 対象 | 役ごと | 主セッションを含む作業全体 | 役(サブエージェント)の中だけ |
| 対応 | Claude Code | Claude Code・Codex・Cursor・Gemini CLI・pi など多数 | Claude Code(pi 用は準備中) |
| 導入 | ファイルを置く | `/plugin install` | 仮想環境に入れ、`assemble.sh` で役とスキルを置き、`settings.json` に hook を登録 |

違いが一番はっきり出るのは、役が手順を守らなかったときです。たとえば builder が、テストを書いてすぐ実装し、一度も落ちるところを観ずに「テスト通りました」と報告したとします。

- **superpowers**: 「落ちるのを観る」はスキルに書いてあります。守るかどうかはモデル次第で、守らなかった報告もそのまま主セッションに届きます。
- **raiya-plugin**: hook がそのテストの実行を記録しています。落ちた実行が記録に無ければ、報告を役に差し戻します。

superpowers は、手順そのものの質で勝負するツールです。15 本のスキルが開発の流れ全体(設計・計画・実装・レビュー・ブランチの片付け)を覆い、対応するエージェントも多数あります。raiya-plugin は、その手順を役の定義の土台に借りたうえで、「書いてあっても守られないことがある」部分だけを形式で検査します。手順の広さでは superpowers に及びません。違いは、守られなかったときに気づけるかどうかです。

## どこまで確かめられたか

正直に書きます。

- 決定論のテストは 227 本あり、すべて通ります。これは「hook がそういう構造になっている」という確認です。
- Claude Code の実機では、2026-11-14 に、`description` の無い Bash の拒否、欄の無い報告とテストが落ちるのを観ていない報告の差し戻し、規則のリポへの書き込みの拒否を観ました。
- 一方、`残した仮のもの: 無し` が嘘のときの差し戻しは、実機では出ませんでした。役が正直に path を書いたためで、この部分はテストでしか確かめていません。
- 同時に動く役の変化を取り違える問題があり、Bash が走っていた間の変化だけを見る形に改めました。改めた形は、まだ実機で確かめていません。
- 同じ不備を繰り返したときに前例を添えることは、Claude Code の実機で 2026-11-15 に観ました。
- 2026-11-19 に、Claude Code の実機で小さなゲームを 1 本作らせ、architect → builder → qa-reviewer → shipper を通しました。
  - architect が規則のリポを名指した Bash は止まり、前例の 1 文(2 回目)が添えられました。役はそのあと規則どおりに読み直しました。
  - 前の役の報告は、hook が置いたファイルの path で次の役へ渡り、受け手が読めました。
  - builder の「壊して落ちるのを観る」段では、壊しても通ってしまうテストが 3 本見つかり、builder が落ちる形に直しました。
  - 一方、builder はテストのコマンドにパイプを付けるなど手順を 2 回外しました。hook はここを止めず、builder が自分で報告に書いたことで分かりました。
- architect の数え違いは、hook を入れても無くなりませんでした(6 回中 6 回)。いまは architect にも bash を持たせています。持たせたあとの 1 回(2026-11-19)では、報告にある数はどれも、役が自分で走らせた `wc -l` やテストの出力と合っていました。道具の出力から写していない目安の数には、「概算」と書いてありました。まだ 1 回なので、直ったとは言えません。

hook は、役を賢くするものではありません。誤りが通り抜けたときに見えるようにするものです。

## 止めきれないもの

hook は、ツールの呼び出しを 1 つずつ字で見て止めます。役がその字を避ければ通ります。

- 見えるのは、字に現れた形だけです。変数や `cd` の重ねで組んだ path、スクリプトの中から呼んだコマンドは見えません。
- hook が見るのは役の呼び出しだけで、リーダー(主セッション)の呼び出しは見ません。
- 報告の検査は、形(欄の有無・呼び出しの順序)だけを見ます。中身が正しいかは見ません。

根本の対策は、役が使える道具と権限を絞ることです(サンドボックス、git の権限、保護されたブランチ、CI)。これは hook の外で用意する必要があります。raiya-plugin の hook は、規則を届けて、よくある踏み外しをその場で止めるためのもので、悪意や回避を防ぐ仕組みではありません。ここが、いまの確かめる側の限界です。

## おわりに

エージェントが報告を盛る・手を抜く・担当外に出る、という振る舞いを並べてみると、人の失敗の分類とほとんど同じ形をしていました。どれが一度直せば消え、どれが繰り返すのかを先に分けておくと、プロンプトで済むものと仕組みが要るものの線が引けます。
