## この記事について

第2回では Lisp / Python / Sprout を「自己書き換えのしやすさ」で比較しました。今回は、「AIが自らを書き換えること」を前提とした言語 Sprout の主な設計要素——**効果台帳**・**コンパイラ型統合**・**3つのゲート**・**極性システム**——について、「なぜそれが必要なのか」をまとめます。

## 1. なぜ「効果台帳（ledger）」が必要か

### 台帳とは

Sproutでは、副作用（効果）はコードを実行した瞬間には発動しません。**保留効果**として台帳に記録され、後で条件が揃ったときに初めて発動（発芽）します。

### なぜ即時実行させないのか

理由は3つあります。

1. **癖を目に見える形にするため** — 効果が記録として残るので、「このプロセスは何を繰り返し積み重ねてきたか」を後から検査できます。実行の様子を観察しなくても、記録を見れば分かります。
2. **一回の入力で人格が変わらないようにするため** — 発芽には強度のしきい値があり、同じ趣旨の効果がもう一度積まれて初めて実際に効き始めます。単発の入力ではプロセスの傾向は変わりません。
3. **破壊操作の"未処理数"を数えられるようにするため** — 破壊的な操作は記録されたまま残り、その合計が後述の「ゲート2」の判定材料になります。副作用が実行と同時に消えてしまうと、この量自体が定義できません。

### なぜ「台帳だけ」が再起動をまたいで残るのか

自己書き換えするプログラムは、コード自体がどんどん変わっていきます。コードを「そのプロセスが何者か」の拠り所にしてしまうと、書き換えるたびに別人になってしまいます。

そこでSproutは、**「何をしてきたか」の記録（台帳）こそがプロセスの性格**だと定義しました。コード本体（方針層）とルール宣言（価値層）は再起動のたびに初期化されますが、積み重ねてきた効果の記録だけは消えません。自分の性格を変えたいなら、コードを書き換えるのではなく、効果を積み直すか監査（audit）を通すしかない、という設計です。

## 2. なぜ「コンパイラ型統合」（v1.0構想）が必要か

現行実装はまだ動的なVM評価ですが、将来のv1.0では「すべてのコードはコンパイルを経てからしか実行できない」設計への移行が構想されています（未実装・設計段階）。

### そもそもの動機: エラーを実行前に見つけたい

Pythonのようなインタプリタ言語では、型の不一致や存在しない属性へのアクセスといったエラーの多くは、**そのコードが実際に実行されるまで表面化しません**。テストでカバーできていない経路にたまたま処理が到達したときに初めて発覚します。

これは自己書き換えするプログラムにとって特に深刻です。実行時に生成されたコードがそのまま実行系に渡ると、エラーは「壊す操作が動いてしまった後」に見つかることになりかねません。コンパイル時に型を検算する仕組みを持てば、コードが**実行される前**にエラーを検出でき、事前のテスト・検査で弾けます。これがコンパイラ型統合を検討している一番の動機です。

その上で、単に型検査を導入するだけでなく「型推論を持たない」という一段強い設計を選んでいて、これには3つの理由があります。

### 型推論をあえて捨てる

v1.0の型検査器は、書かれた型注釈が正しいかを**確認するだけ**で、型を推測しません。すべての束縛に型注釈が必須になります。普通の言語設計の潮流とは逆行しますが、理由は次の3つです。

- **省略のメリットがない** — 型注釈の省略は「人間が書く手間を省く」ための最適化です。Sproutは書き手がAIであることを前提にしているため、この恩恵はほぼゼロです。
- **推論はブレを見逃す** — AIの生成には確率的なゆらぎがあります。型を推論してしまうと、たまたま辻褄が合っただけのコードも素通りしてしまいます。注釈必須にすれば、ゆらぎは「注釈と実装の不一致」として表面化します。
- **検査器を単純に保つため** — 推論をやめると、検査器は「宣言と実装が一致しているか」を見るだけの単純なものになります。安全性の検査そのものが複雑だと、検査器にバグが紛れ込むリスク自体が上がってしまいます。

### 二重帳簿の原則

型も極性（後述）も、**宣言（注釈）と実装（本体から導かれる実際の値）の2箇所に書かせて、処理系が突き合わせる**方式を取ります。片方だけから検査すると、その情報源自体の誤りには気づけません。2つを独立に書かせて照合することで、誤りが初めて"差分"として見えるようになります。

（例: `add(x: Int): String` と宣言しながら本体で `return x + 1` と実装した場合、宣言側の型 `String` と実装から導かれる型 `Int` の不一致を差分として検知し、コンパイルエラーにします。）

### コンパイルを通らないコードは実行できない（compile-then-run）

ソースコードだけでなく、実行中に自己書き換えで生成されたコード（`enact`されるコード）も、必ず同じコンパイラ・同じ検査を通ります。検査結果は「証明書」としてコードの成果物に添付され、実行系はこの証明書と署名を照合するだけで済みます。検査は重く一度、照合は軽く何度でも、という分担です。

## 3. その他の特徴と理由（駆け足で）

| 特徴 | 何をするか | なぜ必要か |
| --- | --- | --- |
| 3層構造（方針層・価値層・台帳） | コード本体／守るべきルール／効果の記録を分離する | 「どう動くか」は自由に書き換えられても、「何を守るか」は簡単には書き換えられないようにするため |
| 価値層の単調ロック | ルールは追加・強化のみ可、削除・弱化は不可 | 自分に都合よくルールを弱めることを構造的に防ぐため |
| 極性システム（+/-/0） | すべての操作を「建設的・破壊的・中立」に分類する | 「壊す操作」だけをゲートの対象にするために、型のレベルで区別が必要なため |
| 根汚染 | 極性の申告に嘘があると、そのモジュール全体の効果蓄積を凍結する | 申告の一部にでも嘘が混じれば、そのモジュールの申告全部が信用できなくなるため |
| 3つのゲート | 保護ラッパ強制・文脈状態ゲート・価値層単調ロック | 壊す操作を「一律禁止」ではなく「今の自分の状態次第で許可・拒否」にするため |
| トピックは言語の外から与えられる | 効果が発芽する条件（トピック）はホスト側が渡す | プログラムが自分に都合のいい条件を名乗って効果を発芽させる経路を塞ぐため |

## まとめ

Sproutの設計は一見過剰に見える部分が多いですが、その将来の目的は**「AIによる自律的な安全な再帰的自己改善」**の実現です。

- **台帳**は、変化し続けるコードではなく「積み重ねた記録」を信頼の基盤にし、
- **コンパイラ型**は、AIが生成したコードを無条件に信じず必ず厳密に検査し、
- **ゲート**は、プログラムの意図表明（自己申告）ではなく実行時点の客観的な状態を見ます。

どれも「性善説で動く仕組みを作らない」という同一の設計思想から生まれています。システムが自らを書き換え続けても崩壊しない安全性を**“言語の構造”として保証すること**こそが、自律的な再帰的自己改善へ向けた土台となると考えています。
