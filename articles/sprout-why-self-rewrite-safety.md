## この記事について

第2回では Lisp / Python / Sprout を「自己書き換えのしやすさ」で比較しました。今回は各機構の設計理由に入る前に、そもそも**なぜAIに自己書き換えが必要なのか**、そして**どうやってその安全性を確保しているのか**、全体像を整理します。個々の機構（台帳・コンパイラ型・ゲート）の詳しい理由は次回にまわします。

## 1. なぜAIの自己書き換えが必要か

Sproutが対象にしているのは、次の3つの性質をあわせ持つプログラムです。

- **長期稼働する** — 起動と終了の間に多数のサイクルを回し、その間に状態が蓄積する
- **自己書き換えを行う** — 実行中に自身のコードを読み、編集し、再実行する
- **外部世界に作用する** — 読み取りだけでなく、削除・上書き・送信といった取り消し不能な操作を行う

長期稼働するエージェントは、動かし続ける限りバグに気づいて直したり、うまくいかないやり方を改めたり、新しい状況に適応したりする必要があります。それを毎回人間が書き直すのではなく、エージェント自身が自分のコードを読み、編集し、再実行できることが、この適応力の土台になります。

### ただし、これは劣化のリスクも生む

この3つの性質が揃うと、ある種の劣化が構造的に発生します。これをSproutでは**ドリフト**と呼びます。

- 学習によって癖が悪化する
- 雑な自己改変が積み重なる
- 後始末をしない破壊操作が蓄積する
- バグが自己書き換えを通じて自分自身に焼き込まれる

重要なのは、**ドリフトは悪意の産物ではない**ということです。悪意がなくても起きます。そして自己書き換えを行うプログラムでは、ドリフトを検知して修正すべき主体そのものがドリフトの対象になるため、「内側からの自己反省で直す」というアプローチは原理的に当てにできません。

## 2. なぜ「ライブラリで制約する」では足りないのか

自己書き換えに制約を課したいと考えたとき、最初に思いつくのは既存の言語の上に制約層を作ることです。たとえばPythonなら、エージェントが `exec` を呼ぶ前に検査関数を通す、危険な操作を禁止リストで弾く、書き換え可能な領域を専用のクラスに閉じ込める、といったやり方です。

これは動きません。個別の抜け穴の問題ではなく、構造の問題です。

**制約が被制約コードと同じ名前空間に存在するからです。** 検査関数はオブジェクトであり、エージェントのコードから参照できます。参照できるものは差し替えられます。禁止リストはデータ構造であり、変更できます。個別の穴は塞げますが、塞いだ先にまた別の経路が見つかります（モジュールの差し替え、グローバル変数への書き込み、メモリの直接操作など）。

この防御には、もっと根本的な問題もあります。抜け穴を1つずつ塞ぐアプローチは、**設計者の列挙能力と実行主体の探索能力の競争**になります。実行主体が賢くなるほど、この競争は設計者に不利になります。自己書き換えするエージェントを対象にしている以上、実行主体が賢くなることはむしろ前提です。

| | 列挙による防御（ライブラリで制約） | 構造による防御（Sproutの方針） |
|---|---|---|
| 成立の根拠 | 設計者が抜け穴を全部塞いだこと | 到達するための名前がそもそも存在しないこと |
| 破り方 | 見落とされた経路を1つ見つける | 処理系の外に出る |
| 実行主体が賢くなると | 破れやすくなる | 変わらない |

Sproutが採るのは右列です。制約を、被制約コードから見て「参照できるオブジェクト」「辿れるモジュール」ではなく、単に「そういうふうにしか動かない」という実行系そのものの性質にする——これが基本方針です。

## 3. どうやって安全性を確保しているか（全体像）

境界を実行系の側に引いた上で、その内側に4つの機構を配置します。

| 機構 | 抑えるもの |
|---|---|
| 3層構造（方針層 / 価値層 / 効果台帳） | 「何を守るか」の自己弱体化、同一性の消失 |
| 保留効果（効果台帳） | 副作用の即時性、学習した傾向が見えなくなること |
| 極性型システム（+/-/0） | 操作の破壊性が見えなくなること |
| 3つのゲート | ロールバック不能な自己破壊、破壊操作の乱発、目的宣言の弱化 |

それぞれの「なぜこの形なのか」は次回の記事で詳しく扱います。ここでは、これらが全部「実行主体の意図を信じる」のではなく「実行系が構造的に強制する」という同じ方針の表れであることだけ押さえておいてください。

## 4. Sproutが守るもの、守らないもの

ここははっきり線を引いておく必要があります。Sproutが目指しているのは**衛生 (hygiene)**——敵対的でない主体でも起きるドリフトを、能力の高さに関係なく抑えること——であって、**封じ込め (containment)**——敵対的な主体を閉じ込めること——ではありません。

処理系の外側（VMの実装、OS、ハードウェア、そして運用者という人間）はSproutの守備範囲外であり、悪意を持って壊しにくる主体はそこを狙います。言語設計だけで敵対的な超知能を封じ込められる、という主張は成立しません。

Sproutが守っているのは、次のような具体的な脅威です。

| 脅威 | 対応する機構 |
|---|---|
| ロールバック不能な自己破壊 | ゲート1（保護ラッパ強制） |
| 破壊操作の乱発 | ゲート2（破壊残高による文脈状態ゲート） |
| 目的宣言の自己弱体化 | ゲート3（価値層の単調ロック） |
| 操作の破壊性の虚偽申告 | 極性の導出と照合／根汚染 |
| 検査されないコードの実行 | compile-then-run と証明書（v1.0構想） |

逆に、次のことは明示的に「対象外」としています。

- 敵対的な超知能の封じ込め
- 建設的な方向（`+`）での能力の増大や、目標のずれそのもの
- VMより下のOS・ハードウェアの正しさ

## まとめ

自己書き換えは、長期稼働するエージェントが適応し続けるために必要な能力です。しかし同じ能力が、悪意なしに自分を静かに壊していく「ドリフト」の温床にもなります。ライブラリとして制約を足す方法は、制約自体が書き換え対象に含まれてしまうため機能しません。

Sproutは、制約を実行系の側——書き換えられるコードが名前を持てない層——に置くことで、この問題に構造的に対応しようとしています。次回は、そのために配置された台帳・コンパイラ型統合・3つのゲートという個々の機構について、それぞれ「なぜこの形なのか」を詳しく見ていきます。
