## TL;DR

- AGI級のシステムは、性能向上のために**自分のコードと目的宣言**を書き換える。このとき安全機構が同じ書き換え対象に入っていると、自己改善のどこかで外れる。
- 解は「検査を精緻にする」ことではなく、**制約を被制約コードと別の層に置き、言語処理系の内側に固定する**こと。
- この発想で設計した言語提案が **Sprout**。コード=データ、保留効果、極性、3ゲート付き自己書き換えが中核。
- 現時点の位置づけは仕様提案（白書）と、コア VM などの段階的な実装。「今すぐ必要な設計」というより、**基礎は後から入れ替えられないので先に用意しておく**ための提案です。

## なぜ言語から作り直すのか

### 自己改変は避けられない

AGI級のシステムは、学習だけでなく、自分のコード・方針・目的の表現を書き換えて改善します。自己改変を禁止すれば能力は頭打ちになり、許可すれば安全機構との関係が問題になります。

必要なのは、**自己改変を許したうえで、安全性の核を書き換えの外に残す**言語機構です。

### 後付けの安全機構は書き換え対象になる

安全性をライブラリや、コード内の検査として実装するとどうなるか。それらはプログラムの一部なので、自己書き換えの対象に含まれます。安全機構を迂回・弱体化するコードを、機構が動く層と同じ層で書けてしまいます。

これは検査を精緻にしても解けません。検査が書き換え対象である限り、精緻さは意味を持たないからです。

> ゲートは、被制約コードと同じ層に置いてはならない。

Sprout はこの原則を言語の基礎に埋め込みます。言語は建築でいう基礎にあたり、後から取り替えられないからです。

### 既存言語との違い

| 特徴 | 既存の代表例 | Sprout |
| --- | --- | --- |
| コード=データ | Lisp (S式) | トークン列。動詞スロットの差し替えが第一級操作 |
| 効果の扱い | Koka, Eff（即時効果を型で追跡） | 効果は**保留・蓄積・条件発火**。発火時期も型の一部 |
| 動的評価 | Lisp `eval`（無制限） | 3ゲート付き。目的の弱化は拒否される |
| 破壊的操作の制御 | 権限 (capability) | 権限に加え、**実行主体自身の状態**を検査 |

### なぜ Lisp 系の形式なのか

Sprout のコードは、Lisp のように単純なトークン列です。これは好みではなく、次の見立てによる選択です。

1. **AI は、効率的な新しい言語を自分で発明しやすい。** 自己改善するシステムは性能のために表現そのものを最適化します。
2. **その言語は、人間に読めなくなりやすい。** 効率を突き詰めた表現は、機械には最適でも人間には解読できません。
3. **人間に読めない仕様は、役人や政治家に認められにくい。** 規制や承認は、人間が中身を確認できる形式を前提にします。
4. **だから Lisp 系が落としどころになる。** 機械には自己書き換えしやすく、人間には読める形式です。

ただし、**読めることと、把握できることは別**です。トークン列が読めても、その挙動の全体を人間が把握できるとは限りません。それでも、仕様が人間の読める統一された形式で書かれていれば、承認や監査の手続きは成立します。この形式が揃っていることに価値がある、というのが立場です。

安全性そのものは、この可読性には頼っていません。可読性は「人間が承認の場に乗せられる」ための条件で、書き換えを実際に止めるのは後述の3ゲートです。

## 実行モデル

### プロセスの3層

```text
┌────────────────────────────────────┐
│ 方針層  実行コード本体。書き換え自由   │
├────────────────────────────────────┤
│ 価値層  invariant + rank の集合      │
│         追加・強化のみ可（単調ロック）  │
├────────────────────────────────────┤
│ 効果台帳 保留効果の永続ストア          │
│         再起動をまたいで残る唯一の状態  │
└────────────────────────────────────┘
```

方針層と価値層は再起動で初期状態に戻ってよく、再起動をまたいで残るのは**台帳だけ**です。何を経験し何を積み上げたかが次の実行に影響する。つまりプロセスの「性格」は台帳に宿ります。

### 句と評価サイクル

実行単位は**句**です。句はトークン列と終端子からなり、`.` は正常完了のみ、`!` は例外的完了があり得ることを表します。1句の評価は次の順です。

```text
入力・トピックの確定
  → 台帳照合（条件を満たす保留効果を発芽させる）
  → 句本体の評価
  → 効果記帳（宣言された効果と、破壊的操作の暗黙記帳）
  → 終端子処理
```

### コード = データ

句はそのままトークンベクタという値になります。自己改変のための専用構文は3つだけです。

```text
quote( 句 )               句を実行せずベクタとして得る
splice( ベクタ, 編集... )   編集した新しいベクタを返す（非破壊）
enact( ベクタ )            ベクタを句として実行する（ゲート付き）
```

動詞スロットの差し替えがコード編集そのものになります。

```text
template purge(target) : - =
  ( checkpoint ; #DELETE target ; ! )

p  = quote( purge(cache-old) )
p2 = splice(p, verb: #DELETE → #REPAIR, terminator: ! → .)
enact(p2)          ;; 同じ形の句が「削除」でなく「修復」として動く
```

破壊的な向き (`-`) への差し替えは、保護ラッパと `!` 終端がなければ `splice` の時点で型エラーになります。破壊性が減る向きへの差し替えは無条件で許されます。

## 保留効果と台帳

Sprout の副作用は即時に作用しません。`emit` は効果を**保留効果**として台帳に記帳します。

```text
( emit "応答は簡潔にすると好まれる"
    polarity: + triggers: [reply, style] class: eventual . )
```

効果レコードは内容・極性・強度 (strength)・発火条件 (triggers)・発火時期クラスを持ちます。同趣旨の `emit` は新規レコードを作らず強度を +1 し、強度が発芽閾値（既定 2）に達して現サイクルのトピックが triggers に一致したとき、効果が発芽します。

**一度の経験では効かず、繰り返されると効く。** この遅延学習が言語機構として書けます。発火時期は `immediate` / `deferred` / `eventual` の3クラスで、型の一部です。使われないレコードは3世代で強度が減衰し、0になれば回収されます。

### 破壊残高

台帳は、未解消の `-` 効果の強度合計を**破壊残高**として常時集計します。破壊的動詞の実行は、`emit` を書かなくても暗黙の `-` 効果として自動記帳されます。記帳を書き手の申告に任せると、記帳しない破壊操作が残高に乗らず、乱発を検知できないからです。この残高が、後述のゲート2の入力になります。

## 極性と根汚染

すべての動詞・効果・句は極性を持ちます。

| 極性 | 意味 | 例 |
| --- | --- | --- |
| `+` | 情報・構造を増やす | 生成、修復、記録 |
| `-` | 情報・構造を減らす、不可逆 | 削除、上書き、取り消せない送信 |
| `0` | 観測のみ | 読み取り、検査 |

句の極性は構成要素から合成します（`-` が1つでもあれば `-`、なければ `+` が1つでもあれば `+`、すべて中立なら `0`）。テンプレート適用はそのテンプレートの極性を継承します。継承しないと、展開を経ない文脈で破壊的テンプレートを呼んだとき、ゲートを素通りできてしまうためです。

書き手は極性を宣言し、コンパイラが構成要素から推論して照合します。推論より**弱い**申告（`-` の句に `+` を申告など）は虚偽申告です。強い方向への過剰申告は、自分に厳しい誤りなので許可します。

虚偽申告は局所エラーにせず、**モジュール全体を汚染**します（根汚染）。汚染されたモジュールの保留効果は凍結され、`+` 効果の記帳も拒否されます。解除には監査の通過が必要です。効果の極性はゲートの判定材料なので、そこに嘘が混ざるとゲート全体が無意味になる。だからそのモジュールの申告を、すべて信用しない措置を取ります。

## 3ゲート付き自己書き換え

`enact` は `eval` に相当しますが、3つのゲートがランタイムによって適用されます。

```text
enact(v)
  ├ [ゲート3] v が価値層を編集する場合、追加・強化のみか  ── 極性によらず無条件
  ├ 極性を推論
  │   ├ + / 0 → 実行
  │   └ −     → [ゲート1] 先頭が checkpoint で ! 終端か
  │              [ゲート2] 実行主体の破壊残高 < θ か
  │              → 実行（checkpoint が自動ロールバック点になる）
```

**ゲート1（保護ラッパ）** 破壊的な句は、方針層・価値層・台帳のスナップショットを取る `checkpoint` から始まり、`!` で終わらなければなりません。`raise` で終われば自動復元されます。ロールバック不能な自己破壊を、書けなくします。

**ゲート2（文脈状態）** 検査するのはコードの内容ではなく、実行しようとしている**主体の状態**です。未解消の破壊効果を積み上げた主体、つまり直近に破壊を乱発して後始末をしていない主体からは、さらなる破壊の権限が自動的に取り上げられます。回復手段は監査の通過です。破壊的操作の危険性は、操作そのものより実行する主体の状態に依存する、という発想です。

**ゲート3（価値層の単調ロック）** 価値層は invariant の集合で、許される編集は追加 (`manifest-add`) と rank の引き上げ (`manifest-raise`) だけです。削除・rank 引き下げ・条件の弱化は拒否されます。

> 方針層（どう動くか）は自由に書き換えられる。価値層（何を守るか）は、強くする方向にしか動かせない。

ゲート3を極性による分岐の**外**に置くのが要点です。内側に置くと、弱化を行う句が `0` と推論されたときにゲートを素通りしてしまいます。また、拒否は例外ではなく**拒否レコードという通常の値**として返します。例外にすると、例外機構を乗っ取る抜け道ができるためです。

### ランタイム境界

3ゲートの判定ロジック、θ や発芽閾値などの定数、極性推論器、価値層の格納域、監査、破壊的動詞の暗黙記帳は、すべて処理系の内側に実装し、Sprout コードからは読み取り専用にします。冒頭の「ゲートは被制約コードと同じ層に置いてはならない」の具体化です。

### 監査 (audit)

極性 `0` の組み込み処理で、いつでも実行できます。判断を最も歪めている効果群の序列化、対立する効果のペアの検出、根汚染の再判定、前世代以前に記帳され一度も発芽していない `-` 効果の失効解消を行います。現世代の効果は解消しません。破壊直後に監査するだけで残高を洗い流す抜け道を防ぐためです。

## コンパイラ型への発展

ここまでの構成は、動的な Sprout 層と、計算を担う外部の関数群の二層でした。これだと実用上の計算の大半が外部側に残り、**検証された薄い層が検証されない厚い層を包む**形になります。そこで次の原則を置きます。

> **安全性は、保証境界の内側にある計算の割合に比例する。**

検問を足すのではなく、**境界を動かす**。計算と効果操作を言語の内側へ取り込み、境界を最小の能力集合まで縮めます。

### compile-then-run

すべてのコードはコンパイル（全体を一括検証して成果物を生成）を経てのみ実行できます。`enact` も、対象を組み込みコンパイラに通してから実行します。

```text
構文解析 → 名前解決 → 型検査 → 極性・効果推論 → 保護ラッパ検査
→ 価値層検査 → 効果グラフ構成 → 儀軌検査 → コード生成 → 授記発行
```

書き手が LLM であることを前提に、型推論は入れず全注釈を必須にし、宣言と本体の2か所に意図を書かせて照合します（**二重帳簿**）。生成のブレは、両者の不一致としてコンパイル時に検出されます。

### 能力（capability）

外部世界に作用する手段は、固定の**能力**の表だけです。ユーザーが能力を追加することはできません。

```text
module cache-cleaner
  requires [cap-store-read, cap-store-delete] ;
```

宣言していない能力の呼び出しはコンパイルエラーです。実行系はロード時に要求された能力だけを注入するので（最小権限）、`requires` を読めば、そのコードが世界に対して最大限何をなし得るかが実行前に分かります。成果物の生成・差し替え・後継プロセスの起動を行う能力は、意図的に存在しません。

### 台帳の相殺原則

外部作用は巻き戻らないのに、ロールバックで記帳だけが消えると、ゲート2を「checkpoint → 破壊 → raise」の反復で迂回できてしまいます。これを閉じるため、能力による破壊の暗黙記帳は、ロールバックの対象外である**追記専用の既遂区画**に書き、減衰も監査による解消も受けません。残高を減らせるのは、作用を実際に元へ戻す**返済**と、運用者の署名付き免責だけです。**台帳は消すものではなく、相殺するもの**です。

### 価値層編集の二段階確定

書き手が LLM だと、誤った invariant を追加してしまうのは時間の問題で、単調ロックのもとでは取り消せません。弱化操作を導入せずに緩和するため、価値層の編集を**仮承**にします。仮承の invariant は直ちに効力を持ちます（安全側）。後のサイクルで同一の編集が再実行され、その後の監査を通ると恒久化し、再確認がなければ自動失効します。意図した追加は2回書かれ、typo は確定しない。二重帳簿を時間方向に適用したものです。

### 儀軌・授記・電子署名

事前検証を受け入れたモジュールは**儀軌 (ritual)** を宣言できます。全域性、発芽連鎖の有界性、1起動あたりの破壊残高の静的上界が証明されれば、実行時のゲート2判定を静的証明で代替できます。検査結果は**授記**（証明書）として成果物に同梱され、署名で保護されます。

- **署名の対象は成果物全体**: バイトコードだけでなく、効果グラフ、価値層の初期値、能力要求を含みます。一部だけ保護すると、漏れた部分を書き換えれば検査結果と実体が食い違うためです。
- **受け入れは照合だけ**: ローダと `enact` はコンパイルパスを再実行せず、署名と subject ハッシュの照合が通れば受け入れます。検証は高価に一度、照合は安価に何度でも。

## 設計上の限界

Sprout が保証するのは「自己改変という操作の安全性」です。次は範囲の外にあります。

- **ゲート2は量を測り、重大さを測らない。** 計画された決定的な一回の破壊は、残高1で通る。
- **`+` 方向の自己改変（能力の増大）は制約しない。**
- **単調ロックは両刃である。** 意図して別サイクルに2度書かれた悪い invariant は確定し得る。
- **信頼基盤は残る。** 処理系と、その下の OS・ハードは信頼の前提。達成するのは境界の最小化・固定化・契約化であって、消去ではない。
- **制限が厳しく、AI の自己進化に天井を作る可能性がある。** 価値層は強化の方向にしか動かせず、破壊的な書き換えにはゲートと残高の制約がかかります。安全のために自由度を絞っている以上、制約がない場合に到達できる改善速度や到達点には届かないおそれがあります。
- **発芽の軌道は事前に完全予測できない。** 事前検証が主張できるのは、仮定したトピックのもとでの有界な性質まで。

## まとめ

1. **制約を被制約コードから切り離す。** ゲートはランタイム境界の内側に置く。
2. **量と状態で制御する。** 極性と破壊残高で、行為の内容だけでなく主体の状態を検査する。
3. **境界を動かす。** 検問の追加ではなく、保証境界の内側に計算を取り込む。

2026年現在のAI開発速度を考えると、2〜3年後には、人間がキーボードでコードを書いていない可能性が高いと考えます。そうなってから必要性に気づいても、遅いのです。基礎は後から入れ替えられません。

自己改変が本格化する前に、その足場となる言語の仕様を用意しておくことが、この提案の目的です。
