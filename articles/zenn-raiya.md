## 仏教書を読んでいて、記憶の話だと気づいた

仏教の唯識(ゆいしき)を読んでいたら、これは記憶のことを書いているのではないか、と思いました。

唯識は、心を八つの層に分けて説明する教えです。その最も深いところにある阿頼耶識(あらやしき)は、経験を「種子」として蓄え、必要なときに芽を出させる倉のようなものだと説かれます。AIエージェントに記憶を持たせたい自分には、設計書に見えました。

そこで、唯識の構造をそのまま処理パイプラインにした記憶ツール「頼耶(raiya)」を作りました。この記事では、唯識のどの部分が記憶の設計になったのかを書きます。

## 唯識の「記憶」の考え方

唯識の記憶観で、設計に効いたものを三つ挙げます。

**1. 経験は種子として蓄えられる(熏習)**
経験は、阿頼耶識に種子として植えつけられます。これを熏習(くんじゅう)といいます。1回の出来事の要約を残すのではなく、経験が積み重なって傾向(性向)になる、という見方です。

**2. 縁がそろったときだけ芽が出る(発芽)**
蓄えた種子が常に表に出るわけではありません。条件(縁)がそろったときにだけ現れます。記憶の想起も、全部を毎回出すのではなく、いま関係あるものだけを出すのが自然です。

**3. 認識には三つの身分がある(三性)**
唯識は、心に浮かぶものを三つに分けます。

| 三性 | 意味 | raiya での扱い |
|---|---|---|
| 圓成實(えんじょうじつ) | ありのままの事実 | ユーザーの発言に逐語で接地した記憶 |
| 依他起(えたき) | 縁によって生じたもの | アシスタントの発言にだけ接地した記憶 |
| 遍計所執(へんげしょしゅう) | 実体のないものを思い込んだもの | どこにも根拠がない記憶 = 捏造 |

三つ目がこの設計の核心です。LLMに記憶を任せると、実際には言っていないことが「覚えていること」として混ざることがあります。唯識はこれを、遍計所執として最初から別に数えています。

## 設計に落とす:LLMは「提案」しかできない

三性の考え方から、raiya の中心になる規則が決まりました。

> LLMは記憶を**提案**できる。ただし、その記憶を採用するかどうかは、LLM自身の申告ではなく、決定論のゲートが判定する。

ゲート(`sansho.py`)は、提案された記憶の根拠となる文を、その往復の本文と**逐語一致**で照合します。

- すべての根拠がユーザーの発言に一致する → 圓成實
- アシスタントの発言にだけ一致する → 依他起
- 一致しない根拠が一つでもある → 遍計所執(隔離して、記憶に入れない)

提案に付いてくる「これは事実です」という自己申告のフィールドは、読みません。LLM自身に、自分の記憶が本物かどうかを判定させないためです。

ここにも原典の裏付けがあります。唯識では、善でも悪でもない中立の性質を「無記」と呼びます。ゲートに自己申告を読ませないのは、提案する側が自分の身分を決められない構造にしたかったからです。

## 全体の構造

唯識の三つの変化(三能変)が、そのまま処理の流れになっています。

```
六識(入力・出力)  →  末那識(注入)  ←  阿頼耶識(種子の倉)
 会話の往復を台帳に    いま関係する種子を    種子を植える・併合する・
 追記する             会話に差し込む        発芽させる
```

- **台帳**: 全往復を追記専用で記録します。削除も更新もしません。
- **統合**: 往復が5件たまると、LLMが台帳の窓をまとめて読み、記憶の候補(決定、回避策、所在、再開点、性向)を提案します。ゲートを通ったものだけが種子になります。
- **想起(末那識)**: プロンプトごとに、発芽した種子とその索引を、決定論的に選んで会話に差し込みます。このとき台帳は読まず、LLMも呼びません。
- 種子は削除も減衰もしません。唯識の「業は消えない」という考え方に合わせました。

Claude Code の hooks に登録すると、これが会話のたびに自動で動きます。コアの実装は SQLite 1ファイルと PyYAML だけで(MCPサーバを使う場合だけ公式のMCP SDKが加わります)、詳細はリポジトリの README に書いています。

## 似たツールとの比較

Claude Code 向けの記憶ツールは他にもあります。設計の違いを表にしました。claude-mem と sui-memory の欄は、各ツールの公開情報から私が読み取った内容です。

| | claude-mem | sui-memory | raiya |
|---|---|---|---|
| コード量 | 大規模 | 1,759行 | 約10,000行 |
| 言語 | TypeScript | Python | Python |
| 記憶の保存 | LLMで要約・圧縮 | 生のtranscriptをチャンク化 | 生の往復を台帳に追記し、まとめてLLMで「記録」に統合 |
| 捏造の扱い | 要約を信頼する | 生の本文なので混入しない | 逐語一致のゲートで遮断 |
| トークン消費 | 毎メッセージ数千 | ゼロ(LLM不使用) | 想起はゼロ。統合のとき(5往復ごと)だけLLMを1回呼ぶ |
| 検索 | Chroma(外部DB) | SQLite内蔵(FTS5+sqlite-vec) | SQLite内蔵。決定論の条件照合 |
| 外部依存 | ChromaDB等 | sentence-transformers, sqlite-vec | PyYAML(MCPサーバを使う場合は公式のMCP SDKも) |
| セットアップ | 複数プロセス起動 | uv syncのみ | `pip install -e .` とhooksの登録 |

raiya は sui-memory より重く、claude-mem より軽い位置にいます。違いは、記憶を採用するかどうかを決める「ゲート」を持つかどうかです。要約を信頼するのでも、生の本文をそのまま持つのでもなく、LLMの提案を逐語一致で検査して通します。

## どこまで確かめられたか

正直に書きます。

- 決定論のテストでは、根拠のない提案を人工的に与えて、すべて遮断されることを確認しています。これは「ゲートがそういう構造になっている」という確認です。
- 実際のLLMが捏造を提案してくるか、という点は別の問題です。実LLMでの手動テスト(計60往復)では、根拠のない提案は1件も観測されませんでした。「LLMは頻繁に捏造する」と主張できる結果は、手元にはありません。
- 実運用で効くかどうかは、まだこれから確かめます。

## おわりに

仏教の本は、読みものとしても面白いのですが、「心はどういう部品でできているか」という設計の問いに、1000年以上前に答えようとした文書でもあります。今回はそれを実装の設計図として読み実装してみた、という記事でした。
